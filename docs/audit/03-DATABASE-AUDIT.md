## 2. Findings

Severity: **P0** critical/exploitable/data corruption · **P1** high · **P2** medium · **P3** low.
Status: **CONFIRMED** = traced in current source; **POTENTIAL** = reachable path but needs a live DB / prod data to prove.

### A-DB-01 — Transfer accept/complete/cancel/reject are check-then-act races (no atomic state guard) · P1 · CONFIRMED

- **Evidence:** `apps/web/src/app/api/transfers/[id]/accept/route.ts:20-32`, `complete/route.ts:20-60`, `cancel/route.ts:20-30`, `reject/route.ts:20-30`; helper `apps/web/src/lib/transfers.ts:23-36` (`expireIfStale` is a separate non-atomic UPDATE).
- Each route loads the transfer (`loadTransferInOrg`), checks `status` in memory, then issues an unconditional `prisma.websiteTransfer.update({ where: { id }, data: { status: … } })`. The `complete` route's `$transaction` (`complete/route.ts:40-54`) updates the website, deletes assignments/integrations and marks the transfer COMPLETED — but never re-checks `status` inside the transaction, and there is no `updateMany({ where: { id, status: "PENDING_CONNECTION" } })` guard.
- **Reproduction (NOT RUN — needs live DB + two concurrent requests):** two `POST /api/transfers/[id]/complete` calls for the same transfer, both passing the `PENDING_CONNECTION` check before either transaction commits. Both transactions then run: website team flip (idempotent), assignment/integration deletes (idempotent), transfer marked COMPLETED twice, **two** `website.transfer.completed` audit rows, two cache invalidations. Worse, an `accept` racing a `cancel`: both pass their in-memory status checks; the later writer wins and can resurrect a CANCELLED transfer to `PENDING_CONNECTION` (or cancel an already-accepted one and leave the accept's audit row claiming success).
- **Dynamic verification 2026-11-23 (retry, real DB + local app server, scratch org A only): CONFIRMED-BY-EXECUTION — three manifestations.** (1) **Double complete:** two concurrent `POST /api/transfers/cmwtxgqor000gp5zs63vz9iar/complete` both returned **200**, and the audit log shows **two** `website.transfer.completed` rows (23:59:47.525Z and 23:59:47.826Z). (2) **Cancel-then-complete race:** over 6 parallel cancel+complete rounds on fresh transfers, 3 rounds ended **COMPLETED with `completedAt` set despite cancel returning 200** (rounds 2, 5, 6) — the cancelled transfer was resurrected; 1 round returned 409 correctly; 1 round was invalid (initiate failed). (3) **Cancel overwriting a completed transfer:** in round 3 the complete transaction ran (website moved to the destination team, `completedAt` set) and cancel then overwrote the status to **CANCELLED** — final state is internally inconsistent (website handed over, transfer record says cancelled, `completedAt` non-null). The sequential cancel-then-complete path correctly returns 409 `invalid_state / CANCELLED` — the defect is purely the missing atomic guard. Fixture: an ACTIVE `GoogleConnection` row was inserted for the destination team so `complete` could pass its connection check (no real Google account involved). Scratch transfers/org deleted afterwards.
- **Impact:** duplicate completion side-effects; a cancelled transfer can be resurrected into the live state machine; audit trail contradicts final state.
- **Correction:** make every transition a single conditional write, e.g. `updateMany({ where: { id, status: "PENDING_ACCEPTANCE" }, data: { status: "PENDING_CONNECTION", … } })` and treat `count === 0` as `invalid_state` (409); inside `complete`, re-verify status in the transaction (or use the same conditional update as the transaction's final step and abort if it matches 0 rows). Apply the same pattern to `expireIfStale` (conditional `updateMany` on open status + expiry).
- **Regression test:** two concurrent accept/complete/cancel requests against one transfer (test DB or mocked Prisma) — exactly one succeeds, the other gets 409, final status is never a resurrected open state.

### A-DB-02 — Last-SUPER_ADMIN guard is a non-atomic count-then-delete/demote · P1 · CONFIRMED

- **Evidence:** `apps/web/src/app/api/members/[id]/route.ts:78-88` (delete) and `:41-49` (role PATCH): `prisma.user.count({ where: { organizationId, role: "SUPER_ADMIN" } })`, then `if (admins <= 1) return 409`, then an unconditional `prisma.user.delete` / `user.update` — no transaction, no row lock, no DB constraint.
- **Reproduction (NOT RUN — needs live DB + concurrency):** org has exactly 2 SUPER_ADMINs; two admins concurrently delete each other (or demote each other). Both count `2`, both pass, both deletes commit → **zero SUPER_ADMINs**. The org then has no one who can manage members/organization (no code path promotes a non-admin to SUPER_ADMIN without an existing SUPER_ADMIN).
- **Dynamic verification 2026-11-23 (retry, real DB + local app server, scratch org C only): CONFIRMED-BY-EXECUTION.** Org C was created with exactly 2 SUPER_ADMINs (C1 via signup, C2 via invite + role promotion by C1; neither had connections/transfers, so no `member_has_dependencies` interference). C1 `DELETE`d C2 and C2 `DELETE`d C1 concurrently: C2's request returned **200 `{"deleted": true}`**; C1's request returned **400 `invalid_reference`** — but **both users are gone**: org C now has **0 users and 0 SUPER_ADMINs**. The 400 is itself a second defect: C1's delete committed, then its post-delete `writeAudit` failed with a P2003 (`AuditLog.actorId` → C1, deleted concurrently), so the deletion is **unaudited** (only one `member.deleted` audit row exists for the pair, actor nulled via SetNull). The last-admin count guard passed on both requests because each read the count before the other's delete committed. Scratch org C deleted afterwards.
- **Impact:** organisation can be left permanently admin-less; recovery requires direct DB intervention.
- **Correction:** do the guard inside a transaction with a lock (`SELECT … FOR UPDATE` on the admin rows, or a serializable transaction), or enforce at the DB level (e.g. a trigger / deferred constraint that at least one SUPER_ADMIN per org remains). At minimum, wrap count+delete in `$transaction` with an explicit lock — a plain `$transaction` at Read Committed does **not** fix this by itself.
- **Regression test:** concurrent delete/demote of the last two SUPER_ADMINs; final state must retain exactly one.

### A-DB-03 — Concurrent primary mappings collide on the partial unique index and surface as a 409 (not a 500) · P2 (downgraded from P1 on dynamic verification) · PARTIALLY CONFIRMED

- **Evidence:** `apps/web/src/app/api/google/properties/map/route.ts:100-142`. Demote-previous-primary (`updateMany … isPrimary: false`) + `upsert` run in a `$transaction`, but under Read Committed two concurrent `isPrimary: true` maps for the same `(websiteId, provider)` with _different_ `externalId`s can both demote, then both insert `isPrimary: true` — the second insert violates `WebsiteIntegration_one_primary_per_provider` (`20261120000000_stage2_db_integrity/migration.sql:94-96`). The route catches **no** `P2002` (contrast `websites/[id]/transfer/route.ts`, which does handle it, and `websites/[id]/route.ts` PATCH, which maps P2002 → 409 `domain_taken`).
- **Reproduction (NOT RUN — needs live DB + concurrency):** two simultaneous `POST /api/google/properties/map` with `isPrimary: true`, same website+provider, different properties. Expected: one 200, one clean 409/retry. Actual (by code path): the loser throws P2002 into `withApiErrors` → generic 500.
- **Dynamic verification 2026-11-23 (retry, real DB + local app server, scratch org A only): PARTIALLY CONFIRMED — the race is real, the claimed 500 is REFUTED.** Two concurrent primary maps (different GA4 properties, same website+provider) both returned 200 in 3 rounds (transactions serialized via the in-transaction demote), with exactly one primary remaining. With **6 parallel** primary maps, the collision appeared: **4× 200, 2× 409 `{"error":"conflict"}`** (P2002 from `WebsiteIntegration_one_primary_per_provider`), and the final state still had **exactly one primary** — the DB backstop held and the error is a clean 409, not a 500 (`prismaErrorResponse` maps P2002 → 409; the audit's "generic 500" reading was wrong). **Severity downgraded P1 → P2:** no data corruption and no 500, but a legitimate concurrent action spuriously fails and the client must retry; the route should catch P2002 and retry once or return a typed `primary_conflict` 409. Fixture: discovered `GoogleProperty` rows were inserted under a fixture ACTIVE connection (no real Google account).
- **Impact:** user-visible 500 on a legitimate concurrent action; the DB invariant holds (good — the index is the backstop) but the API contract breaks.
- **Correction:** catch `P2002` in the map route and retry once (re-read + demote + upsert) or return 409 `primary_conflict`; consider `SERIALIZABLE` for this transaction or an advisory lock per `(websiteId, provider)`.
- **Regression test:** concurrent primary maps for the same website+provider; one succeeds, the other returns 409 (not 500), and exactly one primary remains.
- **Status:** PARTIALLY CONFIRMED (dynamic verification 2026-11-23: race real, 500 refuted — loser got clean 409 `conflict`, exactly one primary remained). **FIXED 2026-11-24 (Stage 3, A-DB-03):** the map route catches P2002 and retries the whole transaction once (re-read + demote + upsert, same P2002 pattern as the transfer-initiate route); a second collision returns typed 409 `primary_conflict`. No SERIALIZABLE transaction and no advisory lock — the retry closes the observed race and the partial unique index stays the backstop. Regression tests in `route-google-discover-map.test.ts` (retry → 200; double collision → 409 `primary_conflict`; two concurrent primary maps → both 200, exactly one primary remains; all three fail against the old code).

### A-DB-04 — Website PATCH can move / re-status a website with an open transfer · P2 · CONFIRMED

- **Evidence:** `apps/web/src/app/api/websites/[id]/route.ts:49-95` (PATCH). It re-verifies the destination team inside the transaction but never checks for an open `WebsiteTransfer`, and `status` is freely settable from `websiteCreateSchema.partial()` — including `TRANSFER_PENDING`, `SOLD`, `ARCHIVED`.
- **Reproduction (static):** initiate a transfer (website stays with team A), then PATCH the website to team B (or `status: "ARCHIVED"`). The transfer row still says `fromTeamId: A → toTeamId: <dest>`; `complete` then flips `teamId` to the destination and **forces `status: "ACTIVE"`** (`transfers/[id]/complete/route.ts:42-46`), silently un-archiving the site and discarding the manual move.
- **Impact:** transfer bookkeeping (`fromTeamId`, audit) contradicts reality; manual status decisions are silently overwritten at completion.
- **Correction:** reject PATCH team/status changes while an open transfer exists (409 `transfer_in_progress`, mirroring the initiate guard), or at least reject `status` transitions out of the transfer state machine; `complete` should restore the pre-transfer status instead of hard-coding `ACTIVE` (or only flip `PENDING_SETUP` → `ACTIVE`).
- **Regression test:** PATCH team/status during an open transfer → 409; complete after an `ARCHIVED` website → status preserved or explicitly documented.
- **Status:** CONFIRMED. **FIXED 2026-11-24 (Stage 3, A-DB-04):** PATCH rejects team/status changes while an open transfer exists (409 `transfer_in_progress`, mirroring the initiate guard); initiate records `websiteStatusBefore` (new nullable `WebsiteTransfer.websiteStatusBefore`, migration `20261124183053_transfer_status_before`) and `complete` restores it instead of hard-coding `ACTIVE` (legacy transfers with null fall back to ACTIVE). Name/domain/url edits stay allowed during a transfer. Regression tests in `route-websites-teams.test.ts` (PATCH team → 409; PATCH status → 409; PATCH name-only → 200) and `route-transfers.test.ts` (initiate records ARCHIVED; complete restores ARCHIVED; legacy null → ACTIVE); the two 409 tests fail against the old code.

### A-DB-05 — Invite-accept shell-org check and shell-org delete are outside the transaction · P2 · CONFIRMED · FIXED 2026-11-24

- **Evidence:** `apps/web/src/app/api/invites/accept/route.ts:38-63`. The emptiness checks (`memberCount > 1 || teamCount > 0 || …`) run as four separate counts **before** the `$transaction` (`:45-53`, which only covers `user.update` + `invite.update`). The shell-org delete (`:55`) is best-effort **after** the transaction with `.catch(() => undefined)`.
- **Reproduction (NOT RUN):** (a) a second member/team is created in the shell org between the counts and the transaction commit — the user is moved anyway, stranding that data in an org whose only member just left; (b) the shell-org delete fails (e.g. a concurrent insert created a dependent row) and the error is swallowed — an empty orphan org accumulates with no owner path to delete it.
- **Impact:** cross-org data stranding in a race window; orphan shell organisations.
- **Correction:** re-check emptiness inside the transaction with locks, or delete the shell org inside the same transaction and surface failure instead of swallowing it; add a periodic sweep for member-less orgs.
- **Regression test:** concurrent invite-accept + member creation in the shell org; accept must fail with `already_in_organization`.
- **Verification 2026-11-24:** fixed — the four emptiness counts are re-checked inside an interactive transaction with the org + user rows locked (`SELECT … FOR UPDATE`, A-DB-02 pattern); a concurrent member creation now fails the accept with 409 `already_in_organization` (regression test fails 200-against-old-code, passes with the fix). The shell-org delete deliberately stays OUTSIDE the transaction: `AuditLog.organization` is `onDelete: Restrict`, so a shell org with any audit history cannot be deleted at all (an in-transaction delete would roll back legitimate accepts), and the four counted relations are `onDelete: Cascade`, so an in-transaction delete would silently destroy concurrently-created data instead of failing. The delete is now a guarded atomic `deleteMany` (emptiness re-verified in the same statement) with failures logged instead of swallowed, and the worker scheduler sweeps member-less orgs (bounded 100/tick, full empty guard incl. no live pending invites) in its existing 1-minute tick.

### A-DB-06 — Organisation delete revokes Google tokens _before_ the delete transaction · P2 · CONFIRMED · FIXED 2026-11-24

- **Evidence:** `apps/web/src/app/api/organization/route.ts:40-58`. The `revokeConnection` loop (`:40-44`) runs first; only then does `$transaction` delete audit rows + org (`:48-51`). `revokeConnection` (`packages/google/src/tokens.ts:196-216`) clears tokens and sets `DISCONNECTED` immediately.
- **Reproduction (static):** if the delete transaction fails (e.g. a concurrent insert creates an `AuditLog` row the Restrict FK was supposed to protect, or any transient DB error), the request returns 500 but **every Google connection is already revoked and its tokens destroyed** — data loss with no org deletion.
- **Impact:** irreversible credential destruction on a failed delete; the org survives but all its Google integrations are dead and must be re-connected manually.
- **Correction:** revoke tokens _after_ the delete transaction commits (accepting that a crash between commit and revoke leaves live grants — the lesser evil, and the same best-effort posture), or record a "pending deletion" marker and revoke in a compensating step. Log the outcome either way.
- **Regression test:** force the delete transaction to fail (e.g. injected fault) and assert connections/tokens are untouched.
- **Verification 2026-11-24:** fixed — the route now captures the revoke material (encrypted refresh token + AAD parts) before the delete transaction and revokes after it commits, via new `revokeConnectionToken` in `packages/google/src/tokens.ts` (returns whether the Google grant was revoked; best-effort, failures logged in aggregate, never a 500). A plain reorder was unworkable: `GoogleConnection.organization` is `onDelete: Cascade`, so the rows — and their encrypted tokens — are gone once the transaction commits and `revokeConnection` would silently no-op, leaving live grants. No "pending deletion" marker was added. Regression tests in `route-organization-delete.test.ts` (failed transaction → 500, revoke never attempted, org never deleted; success → revoke called after the transaction with the captured material; one revoke failing → still 200); the two revoke tests fail against the old code.

### A-DB-07 — `WebsiteIntegration` has no DB rule tying the property FK to its provider · P2 · CONFIRMED

- **Evidence:** `packages/db/prisma/schema.prisma` `WebsiteIntegration` (four nullable property FKs + nullable `googleConnectionId`, no CHECK); `20261122000000_phase4_db_integrity/migration.sql:95-110` (composite FKs only). Postgres `MATCH SIMPLE` semantics: when `googleConnectionId` is NULL, the composite FK on `(googlePropertyId, googleConnectionId)` is **not enforced at all**, so a row can carry `googlePropertyId` with no connection. Nothing prevents: a `SEARCH_CONSOLE` row carrying a `googlePropertyId`; two property FKs set at once; `isPrimary: true` with `mappingStatus: "UNMAPPED"/"ERROR"`; a `MAPPED` row with no property FK at all.
- **Reproduction (static, by schema):** `INSERT INTO "WebsiteIntegration" (…, "provider"='SEARCH_CONSOLE', "googlePropertyId"='<ga4 id>', "mappingStatus"='MAPPED', …)` — accepted by the DB. Only the map route's application logic prevents it today.
- **Impact:** a future code path (or direct DB write) can create mappings the readers misinterpret — e.g. `getPrimaryIntegration` returns a row whose property belongs to another provider, and `fetchReport` in `packages/google/src/sync.ts:196-213` dispatches on the _integration's provider_ while using `externalId`, so a mismatched FK is silently ignored rather than rejected.
- **Correction:** add CHECK constraints: exactly one property FK set per provider (`provider='GA4' ⇔ googlePropertyId IS NOT NULL AND others NULL`, etc.), `googleConnectionId IS NOT NULL` whenever any property FK is set, and `isPrimary ⇒ mappingStatus='MAPPED'`. Keep the map route as the first line of defence.
- **Regression test:** direct-SQL inserts of each mismatched combination must fail with a CHECK violation.
- **Verification 2026-11-24:** fixed — migration `20261124191149_website_integration_checks` adds three CHECKs (`WebsiteIntegration_provider_fk_check`: exactly the provider's FK set; `WebsiteIntegration_connection_required_check`: a connection whenever any FK is set, closing the MATCH SIMPLE hole; `WebsiteIntegration_primary_mapped_check`: `isPrimary ⇒ MAPPED`). Prisma 7.10 has no `@@check`, so the CHECKs live in the migration only (same pattern as `GoogleConnection_single_owner_check`); the schema is unchanged apart from a comment. The map route now writes the full FK set on every map (other three FKs NULL) so re-mapping a pre-CHECK legacy row heals its stale FK. `benchmark-scale.ts` now seeds a real connection + property per website (its old MAPPED-without-FK rows violated the new CHECKs). Regression tests in `smoke-stage2.ts` (CI smoke, real Postgres): five mismatched inserts rejected naming the violated CHECK, plus two control inserts that must succeed. PRODUCTION RISK: `ALTER TABLE ... ADD CONSTRAINT` validates existing rows — Stage 2 (DB-7) left ambiguous/undiscovered mappings with NULL connection and no FK, and any such row makes `prisma migrate deploy` fail; check the target DB with the pre-flight query in the migration header and repair violating rows before deploying.

### A-DB-08 — Legacy polymorphic owner columns can drift from the typed owner FKs · P2 · CONFIRMED

- **Evidence:** `GoogleConnection` in `schema.prisma` keeps `ownerType`/`ownerId` (NOT NULL, no CHECK) alongside nullable `teamId`/`websiteId`; the only DB rule is the exactly-one CHECK on the typed columns. No constraint ties `ownerType='TEAM', ownerId=X` to `teamId=X`. `packages/auth/src/tenant.ts:34-51` (`assertConnectionScopeForWebsite`) **falls back to the legacy columns** whenever the typed column is NULL, so a drifted row is interpreted by legacy values.
- **Reproduction (static):** `UPDATE "GoogleConnection" SET "teamId"='<team-B>' WHERE "ownerType"='TEAM' AND "ownerId"='<team-A>'` — accepted; scope checks then disagree depending on which column a caller reads (`resolveConnectionForWebsite` uses typed columns only, `assertConnectionScopeForWebsite` prefers typed but falls back to legacy).
- **Impact:** inconsistent authorisation decisions for the same connection; a future reader that trusts legacy columns could serve team A's credentials to team B's website.
- **Correction:** finish the migration the schema comment promises ("dropped in a later release"): drop `ownerType`/`ownerId` once all reads/writes use typed columns, or add a CHECK `(ownerType='TEAM' AND teamId=ownerId AND websiteId IS NULL) OR (ownerType='WEBSITE' AND websiteId=ownerId AND teamId IS NULL)`. Until then, remove the legacy fallback in `assertConnectionScopeForWebsite`.
- **Regression test:** a connection row with divergent legacy/typed owners must fail a DB CHECK (or the scope function must reject it).

### A-DB-10 — Retention pruning is unbounded and never prunes stuck jobs · P2 · CONFIRMED

- **Evidence:** `apps/worker/src/scheduler.ts:177-194`. Four `deleteMany` calls with **no `take`/batch limit** (despite the comment "prune old bookkeeping in bounded batches" at `:177`) run once per tick: `AnalyticsSyncJob` (`updatedAt < 30d`, only `SUCCEEDED`/`FAILED`), `OAuthState` (expired > 1d), `AnalyticsCache` (expired), `AuditLog` (older than `auditRetentionDays()`, default 365, `packages/shared/src/retention.ts:9-13`).
- Two defects: (a) a large backlog (e.g. after a worker outage) makes one tick issue a single long-running `DELETE` that holds locks and blocks the scheduler; (b) `RUNNING`/`RETRYING`/`PENDING` sync jobs are **never** pruned — a job stuck `RUNNING` (worker crash mid-run) accumulates forever, and `lastSuccessfulSync`/`planDueSyncs` only look at `SUCCEEDED`, so stuck rows are invisible to scheduling but visible in storage and in the failed-jobs UI.
- **Impact:** unbounded storage growth of stuck-job rows; periodic long DELETEs under load.
- **Correction:** prune in bounded batches (e.g. `deleteMany … take`-equivalent loop, or `DELETE … WHERE id IN (SELECT … LIMIT 1000)`); add a staleness rule for `RUNNING` jobs older than N hours (mark `FAILED` with `lastError: "stale_running"` or delete), and surface the count.
- **Regression test:** seed 5,000 old finished jobs + 100 stuck `RUNNING` jobs; one tick deletes in bounded batches and the stuck rows are resolved, not left behind.
- **Verification 2026-11-24:** fixed — retention pruning in `apps/worker/src/scheduler.ts` now runs in bounded batches: a `pruneInBatches` helper selects up to 1,000 ids and deletes exactly those rows (Prisma's `deleteMany` has no take/limit), at most 10 batches per table per tick, so a large backlog drains over several ticks instead of one long-running DELETE; the per-tick cap is surfaced in the log (`capped: true`). Stuck jobs are resolved by a staleness rule: a `RUNNING` row older than 6 hours is marked `FAILED` with `lastError: "stale_running"` (not deleted — the failure stays visible in the failed-jobs UI, and the website becomes due again because `planDueSyncs` only looks at `SUCCEEDED`; the row is then removed by the 30-day FAILED prune). The 6-hour threshold is grounded in the BullMQ retry cycle (5 attempts, 60s-doubling backoff capped at 1h — a full cycle completes in well under 6h) and the 15s per-call API timeouts. The 30-day sync-job prune now also covers orphaned `PENDING`/`RETRYING` rows (a PENDING row older than 30d is a manual-sync row whose enqueue failed; a RETRYING row older than 30d is past any possible retry cycle) — this closes defect (b) in full, not just the RUNNING half. The A-DB-05 shell-org sweep in the same file is untouched. Regression tests in `worker-scheduler.test.ts` (3 new tests, all fail without the fix): 5,000 old finished jobs pruned in five 1,000-row batches with 100 stuck RUNNING jobs marked FAILED; pruning capped at 10 batches per tick; no staleness marking under 6 hours. The data-lifecycle doc's retention table is updated to match.

## 5. Cascade / Restrict audit (schema vs data-lifecycle doc)

All `ON DELETE` actions in schema-derived DDL match the migration SQL and the lifecycle doc, with two asymmetries worth recording (not findings on their own):

- `ApiKey.createdById` is **Cascade** while `GoogleConnection.createdById` and `WebsiteTransfer.initiatedById` are **Restrict**: deleting a user silently deletes their API keys but is blocked by their connections/transfers. The asymmetry is defensible (keys are revocable credentials, connections are ownership history) but undocumented — the lifecycle doc should state it.
- `WebsiteTransfer.fromTeamId` is `SetNull` while `toTeamId` is `Restrict`: deleting the source team after a completed transfer nulls history; deleting the destination team of an open transfer is blocked. Acceptable, but `fromTeamId` nulling loses the audit trail of where a website came from.
