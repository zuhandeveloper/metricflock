## Role model (correction to the brief)

The brief names roles `SUPER_ADMIN / ADMIN / MEMBER`. The code has **no `ADMIN` or `MEMBER` roles**. The actual enum is `SUPER_ADMIN / TEAM_ADMIN / TEAM_MEMBER` (`packages/auth/src/permissions.ts:20`, `packages/db/prisma/schema.prisma`, `Role` enum). This doc uses the real names; "ADMIN" in the brief maps to `TEAM_ADMIN`, "MEMBER" to `TEAM_MEMBER`. The distinction matters: several authorization rules key off **per-team `isAdmin` membership**, not the global role (see §3).

## Finding format

## Findings

### A-SEC-01 — P1 — CONFIRMED — Cross-tenant read + mutation: sync/metrics endpoints have no organization filter

- **Files:**
  - `apps/web/src/app/api/sync/failed/route.ts:15-17` — `prisma.analyticsSyncJob.count({ where: { status: "FAILED" } })` and `findMany({ where: { status: "FAILED" }, … })`. No `organizationId` (and no join through `website.organizationId`) anywhere in the file.
  - `apps/web/src/app/api/sync/requeue/route.ts:20` — `prisma.analyticsSyncJob.findUnique({ where: { id: body.data.jobId } })`. No org check before the status check, the `enqueue()` call, or the `update({ status: "PENDING" })`.
  - `apps/web/src/app/api/metrics/route.ts:24-33` — `prisma.analyticsSyncJob.groupBy({ by: ["status"], where: { updatedAt: { gte: since } } })` and `findFirst({ where: { status: "FAILED" } })`. No org filter.
- **Evidence:** every other tenant-scoped route in the repo filters by `organizationId: auth.user.organizationId` (e.g. `api-keys/route.ts`, `teams/route.ts`, `websites/route.ts`). These three do not. `AnalyticsSyncJob` has a `website` relation (`schema.prisma:496-510`) through which the org could be reached, but none of the three queries uses it. `sync/requeue` then writes its audit row under the _caller's_ `organizationId` (`route.ts:52-60`), so a cross-tenant requeue is also mis-attributed in the audit trail.
- **Reproduction (NOT RUN — no DB):** create orgs A and B with failed sync jobs; as SUPER_ADMIN of A, `GET /api/sync/failed` and `POST /api/sync/requeue { jobId: <B's job id> }`. Expected per the code: B's jobs are listed (with `websiteId`, `type`, `attempts`, `lastError`, `payload`) and B's job is re-queued and flipped to PENDING.
- **Dynamic verification 2026-11-23 (retry, real DB + local app server, scratch orgs A/B only): CONFIRMED-BY-EXECUTION.** A FAILED `AnalyticsSyncJob` row was created for org B's website (`audit-b-failed-job-00000001`, website `cmwtxffq2000cp5zsp829sjhw`). As org A's SUPER_ADMIN, `GET /api/sync/failed?limit=50` returned **200 with B's job, including its payload** (`{"org":"B","source":"audit-fixture"}`), `websiteId`, `type`, `attempts`, `lastError`. `GET /api/metrics` as org A also counted it (`sync24h.byStatus.FAILED: 1`, `dlq.failed24h: 1`). `POST /api/sync/requeue { jobId: <B's job> }` as org A located the foreign row, passed the `FAILED` status check and reached `enqueue()` — it returned `queue_unavailable` (503) only because no Redis was available in the sandbox, **not** because of any authorization check; with Redis up the requeue would execute and flip the row to PENDING under org A's audit attribution. Unauthenticated `GET /api/sync/failed` correctly returns 401 — the gap is tenant scoping, not missing auth. Scratch orgs deleted afterwards; real orgs untouched.
- **Impact:** multi-tenant isolation breach. Any SUPER_ADMIN of any tenant can enumerate other tenants' sync failures (website IDs, provider error text) and mutate another tenant's queue. Sensitivity of the leaked fields is moderate (`payload` is currently `{ websiteId, manual }`; `lastError` is sanitized — see §6), which is why this is P1 rather than P0, but the _mutation_ (requeue) crosses the tenant boundary with write effects.
- **Correction:** scope all three queries to the caller's org (`where: { status: "FAILED", website: { organizationId } }` for `sync/failed`; `findFirst({ where: { id, website: { organizationId } } })` for requeue; same join for `metrics`). Add a `website.organizationId` composite guard at the DB layer if feasible.
- **Regression test:** CI smoke test with two orgs asserting `GET /api/sync/failed` returns only the caller's org jobs and `POST /api/sync/requeue` with a foreign `jobId` returns 404; unit test on the query construction is not sufficient.
- **Status:** CONFIRMED (code). Dynamic exploitation NOT RUN. **Dynamic verification 2026-11-23 (retry): CONFIRMED-BY-EXECUTION** (see above).

### A-SEC-02 — P1 — CONFIRMED — No fresh-session / MFA step-up on destructive or privilege-minting routes

- **Files:** `apps/web/src/app/api/organization/route.ts` (DELETE whole org, `confirmSlug` only), `apps/web/src/app/api/api-keys/route.ts` (POST mints a persistent org-wide credential), `apps/web/src/app/api/members/[id]/route.ts` (PATCH role / DELETE member), `apps/web/src/app/api/transfers/[id]/complete/route.ts`, `apps/web/src/app/api/google/connections/disconnect/route.ts`.
- **Evidence:** `packages/auth/src/server.ts` configures `session.freshAge: 60 * 15` (15 min) with the comment "sensitive operations … require a session fresher than 15 minutes" — but better-auth enforces freshness only on _its own_ endpoints (via `sensitiveSessionMiddleware`: change-password, change-email, delete-user, 2FA, revoke-session). A repo-wide grep for `fresh` in `apps/` and `packages/` finds **no freshness check in any app route**. Sessions live 30 days sliding (`expiresIn: 30d`, `updateAge: 24h`, `server.ts`), so a session stolen on day 1 (or left on a shared machine) can still delete the entire organization or mint an API key on day 29 with no re-authentication.
- **Reproduction (NOT RUN — no DB):** authenticate, age the session past 15 min (or steal the cookie), `DELETE /api/organization { confirmSlug }` — code path performs no session-age check.
- **Dynamic verification 2026-11-23 (retry, real DB + local app server, scratch org A): CONFIRMED-BY-EXECUTION.** Org A's SUPER_ADMIN session was aged in the DB to 30 days old (`createdAt` 2026-10-25, still unexpired). With that session: `POST /api/api-keys { name: "audit-stepup-key" }` → **201**, full secret returned; `DELETE /api/api-keys/<id>` → **200**; `GET /api/organization/export` → **200** (full org export, 7,564 bytes). No route performed any session-age/freshness check. Scratch key deleted; scratch org deleted afterwards.
- **Impact:** session theft / stale-session abuse escalates directly to org destruction and persistent credential minting. Combined with A-SEC-08 (2FA never enforced), there is no second factor anywhere on the highest-impact actions.
- **Correction:** add a `requireFreshSession(maxAgeSeconds)` helper (better-auth `auth.api.getSession` returns `session.createdAt`/`updatedAt`; or call the fresh-session endpoint) and enforce ≤15 min freshness on org DELETE, API-key create/revoke, member role change/delete, and transfer completion. Consider requiring 2FA-enabled for SUPER_ADMIN (A-SEC-08).
- **Regression test:** smoke test asserting `DELETE /api/organization` with a session older than 15 min returns 401/403; unit test for the helper.
- **Status:** CONFIRMED (code). Dynamic NOT RUN.
- **Dynamic verification 2026-11-23 (retry): CONFIRMED-BY-EXECUTION** (see above) — a 30-day-old session minted and revoked an API key and exported the org with no re-authentication.

### A-SEC-03 — P1 — POTENTIAL — Seed creates a known-credential SUPER_ADMIN when `NODE_ENV` is not exactly `production`

- **File:** `packages/db/src/seed.ts:9-21`. Production refusal is gated on `process.env.NODE_ENV === "production"`; otherwise the password defaults to `"ChangeMe123!"` for `demo@example.com` (SUPER_ADMIN, `emailVerified: true`).
- **Evidence:** the guard keys off `NODE_ENV`, not off the database being seeded. Running the seed with `NODE_ENV` unset (the common case for a one-off `pnpm db:seed` against a remote `DATABASE_URL`) creates the known-credential admin in whatever database `DATABASE_URL` points at — including production. The seed _does_ refuse when `NODE_ENV=production` and `SEED_DEMO_ADMIN_PASSWORD` is unset, which is the only thing standing between this and a prod incident.
- **Reproduction / verification: NOT RUN** — requires inspecting the production database for `demo@example.com` (the open DB-5 item in memory: only Gulzaib can check). Do not "verify" this by running the seed.
- **Impact:** known email + known password + SUPER_ADMIN + pre-verified email = full org takeover of the seeded org if the row exists in prod.
- **Correction:** refuse to create the demo admin unless `SEED_DEMO_ADMIN_PASSWORD` is set, regardless of `NODE_ENV`; additionally refuse when `DATABASE_URL` does not look like a local/dev host. Document a prod check query for `demo@example.com`.
- **Regression test:** test asserting seed exits non-zero with no password env var under `NODE_ENV` unset / `development` / `test` when `DATABASE_URL` is non-local; plus a manual prod-DB check (Gulzaib).
- **Status:** POTENTIAL (code footgun confirmed; prod exposure NOT RUN).

### A-SEC-04 — P2 — CONFIRMED — Open self-registration through the mounted better-auth handler

- **Files:** `apps/web/src/app/api/auth/[...all]/route.ts:9` re-exports `authHandler` (`packages/auth/src/handler.ts`, `toNextJsHandler(auth)`); `packages/auth/src/server.ts:38-49` (`emailAndPassword.enabled: true`, `requireEmailVerification: true`, `minPasswordLength: 12`).
- **Evidence:** the mount exposes the full better-auth surface, including `POST /api/auth/sign-up/email`. Anyone can create an account and, via the `user.create.before` hook (`server.ts:111-160`), a fresh organization in which they are SUPER_ADMIN. There is no invite-only mode, no CAPTCHA, and no allow-list. better-auth's own rate limit (`server.ts:176-188`: `/sign-up/email` 3 per 10 s) is its in-memory store, per instance. Email existence is enumerable: better-auth `dist/api/routes/sign-up.mjs:210` throws `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL` for a taken email (verified in installed `better-auth@1.7.26`).
- **Impact:** unbounded org/account creation (abuse, spam, resource exhaustion); account-enumeration oracle for targeted phishing/password-spray. Mitigated in part: sign-in requires verified email, passwords are scrypt-hashed by better-auth, and self-signup creating a _fresh_ org is the documented product behaviour ("Public sign-ups without an invite still get their own workspace", `apps/web/src/app/(app)/members/page.tsx`).
- **Correction:** decide explicitly whether open registration is a product requirement; if yes, record it and add CAPTCHA/bot defence and per-IP account-creation alerting; if no, disable `emailAndPassword` sign-up or gate it behind an invite. Return a generic response on duplicate-email sign-up if enumeration is unacceptable.
- **Regression test:** smoke test asserting sign-up rate limiting and (if changed) the duplicate-email response shape.
- **Status:** CONFIRMED (code + installed library). Dynamic NOT RUN.

### A-SEC-05 — P2 — CONFIRMED — Rate-limit identity is a client-spoofable header when not behind Vercel

- **File:** `packages/shared/src/rate-limit.ts:87-96` (`clientIpFromHeaders`): trusts `x-real-ip` verbatim, else the first `x-forwarded-for` entry. Used by `apps/web/src/app/api/auth/login/route.ts:22`, `apps/web/src/app/api/google/oauth/callback/route.ts:17`, and (via `rateLimit`) invite creation.
- **Evidence:** no code strips or validates these headers, and nothing in the repo pins the deployment to a proxy that overwrites them (the comment claims "the hosting platform (Vercel) sets [x-real-ip] … and clients cannot spoof through it" — true on Vercel, false for the `docker-compose.yml` / plain-Node self-host path, where a client can send any `x-real-ip` and mint a fresh rate-limit bucket per request). The same untrusted value is stored as the audit `ipAddress` in most routes (`req.headers.get("x-forwarded-for")`, full chain, attacker-controlled).
- **Impact:** login throttling (10/min + better-auth 3/10 s), OAuth-callback throttling (20/min), and invite throttling (20/min) are bypassable by header rotation on non-Vercel deployments; audit IPs are forgeable.
- **Correction:** only trust `x-real-ip`/`x-forwarded-for` when a `TRUST_PROXY` (or equivalent) flag is set for the deployment; otherwise key on the socket address. Store only the first _trusted-proxy-appended_ address in audit rows, and document the Vercel assumption in `docs/security/`.
- **Regression test:** unit test for `clientIpFromHeaders` under both trust modes; smoke test asserting a spoofed `x-real-ip` does not reset the login bucket when `TRUST_PROXY` is off.
- **Status:** CONFIRMED (code). Deployment-dependent; live bypass NOT RUN.

### A-SEC-06 — P2 — CONFIRMED — One unpinned action in a privileged `pull_request_target` workflow

- **File:** `.github/workflows/label.yml:21` — `uses: actions/labeler@v7` (mutable major-version tag). It runs on `pull_request_target` with `permissions: pull-requests: write`.
- **Evidence:** every other `uses:` in `.github/workflows/` is a full 40-char SHA (`actions/checkout@11d5960a…`, `actions/setup-node@949feb24…`, `pnpm/action-setup@b906affc…` / `@f40ffcd9…`, `gitleaks/gitleaks-action@dcedce43…`, CodeQL actions). `label.yml` is the sole exception, and it runs in the highest-privilege trigger context (`pull_request_target` executes workflow code with repo secrets against PR content). A moved/compromised `v7` tag would execute attacker-controlled code with `pull-requests: write`.
- **Correction:** pin `actions/labeler` to its full commit SHA (same convention as the other workflows) and add a CI check that rejects non-SHA `uses:` entries.

- **Status:** CONFIRMED. (Also noted: `ci.yml` uses `pnpm/action-setup` v4 SHA `f40ffcd9…` while `scheduled-maintenance.yml` uses v6 SHA `b906affc…` — both SHA-pinned, but the version drift should be reconciled; P3 observation.)

### A-SEC-07 — P2 — CONFIRMED — No rate limiting on 47 of 52 API routes, including all live-Google analytics routes

- **Evidence:** repo-wide grep for `rateLimit(` in `apps/web/src/app/api` finds only four call sites: login (`auth/login/route.ts:23`), OAuth connect (`google/oauth/connect/route.ts:13`), OAuth callback (`google/oauth/callback/route.ts:18`), invite creation (`members/invite/route.ts:17`). `requireApiKey` adds a 120/min per-key limit for the five v1 routes (`apps/web/src/lib/api-key-auth.ts:37`). The nine analytics routes (`apps/web/src/app/api/analytics/*/route.ts` → `apps/web/src/lib/analytics-handler.ts`) have **no per-user/per-org limit at all** — the only throttle is the single-flight Redis lock and the worker-side `google:<connectionId>` 30/min limit (`packages/google/src/sync.ts:243`), which does not cover on-demand live fetches. Likewise unthrottled: org export/delete, teams/websites/members writes, transfers, sync trigger, reports/send-test, properties/discover (which fans out to three Google list APIs with up to 10 pages each).
- **Impact:** any authenticated low-privilege user (TEAM_MEMBER) can burn the org's Google API quota / drive cost and load the DB (unbounded export, discovery upserts) with no per-account brake. better-auth's own global limit (100/min, in-memory) covers only `/api/auth/*`.
- **Correction:** add a shared authenticated rate-limit wrapper (fail-closed when Redis is configured, per user+route, stricter for analytics/discover/export) and apply it to all mutating and all Google-touching routes.
- **Regression test:** smoke test asserting 429 after N rapid analytics calls; unit tests for the wrapper.
- **Status:** CONFIRMED (code). Live quota burn NOT RUN.

### A-SEC-08 — P2 — CONFIRMED — 2FA is available but never enforced, including for SUPER_ADMIN

- **File:** `packages/auth/src/server.ts:193-197` — `twoFactor({ issuer: "MetricFlock" })` plugin enabled; `User.twoFactorEnabled` exists (`schema.prisma`). No route, page, or policy requires it.
- **Evidence:** grep finds no `twoFactorEnabled` check in `apps/` or `packages/` outside the schema and better-auth internals. The login wrapper handles `twoFactorRedirect` (`apps/web/src/app/api/auth/login/route.ts:48-53`), so enrolled users get TOTP — but enrolment is voluntary for every role, including the SUPER_ADMIN who can delete the org and mint API keys.
- **Impact:** the entire privileged surface rests on a single password (min length 12, scrypt — good, but still single-factor).
- **Correction:** require 2FA enrolment for SUPER_ADMIN (and ideally for any `member.manage`/`organization.manage` holder); enforce at login with a grace/ enrolment flow; re-check before org DELETE / API-key creation (see A-SEC-02).
- **Regression test:** smoke test asserting a SUPER_ADMIN without 2FA cannot complete org DELETE after enforcement; unit test for the enforcement helper.
- **Status:** CONFIRMED (code). Dynamic NOT RUN.

### A-SEC-09 — P2 — CONFIRMED — API keys never expire, have no scopes, and confer full org read

- **Files:** `apps/web/src/lib/api-key-auth.ts:48-52` (synthetic user `{ role: "SUPER_ADMIN" }` for any valid key), `packages/shared/src/api-keys.ts` (`generateApiKey`, `mf_` + 32 random bytes, SHA-256 hash stored — good), `apps/web/src/app/api/api-keys/route.ts` (create: name only, no expiry/scope fields; `schema.prisma:168` `ApiKey` has no `expiresAt`/`scopes` columns), `apps/web/src/app/api/v1/websites/route.ts:15` (`take: 500`, org-wide).
- **Evidence:** a key grants organization-wide read across all five v1 endpoints regardless of which teams the creator administers; the key survives the creator's demotion (only creator _deletion_ cascades the key, `onDelete: Cascade` on `createdBy`); there is no rotation flow and no expiry. Rate limit is 120/min per key. Storage itself is sound (hash-only, format-checked before DB lookup, `lastUsedAt` fire-and-forget).
- **Impact:** a leaked key is a permanent, full-org read credential (websites, portfolio totals, earnings insights, health) until someone manually revokes it.
- **Correction:** add `expiresAt` (default e.g. 90 days, max 1 year) and per-key scopes (at minimum read-only v1 subsets), a rotation endpoint, and revoke-on-demotion/role-change for the creator; surface expiry in the keys UI.
- **Regression test:** unit tests for expiry enforcement in `requireApiKey`; smoke test asserting an expired key returns 401 and a revoked key returns 401.
- **Status:** CONFIRMED (code). Dynamic NOT RUN. **Fixed 2026-11-24 (Stage 3):** `ApiKey` gained `expiresAt` (optional, max 1 year) and `scopes` (empty = legacy full access); `requireApiKey` enforces both (expired → 401, wrong scope → 403 `insufficient_scope`); mint accepts both fields, list returns them, rotation endpoint added (`POST /api/api-keys/[id]/rotate`), expiry/scopes surfaced in the keys UI. Revoke-on-creator-demotion NOT done — member role-change routes are out of this fix's scope; tracked as a follow-up. Regression tests in `api-key-auth.test.ts`, `api-keys.test.ts`, `api-keys-expiry-scopes.test.ts`, `ApiKeyManager.test.tsx`.

(3) The smoke test (`scripts/smoke-test.sh`, read only — runs in CI only) covers cross-org website creation, cross-org OAuth connect, connection visibility for team-admin, transfer 403/200, role-escalation via `/api/auth/update-user`, and OAuth state replay/expiry — it does **not** cover A-SEC-01 (no second org with failed jobs), A-SEC-02, or A-SEC-05.

## Auth flows (revalidated)

- **Signup:** `POST /api/auth/sign-up/email` (better-auth) → `user.create.before` hook assigns org/role server-side; `input: false` on `role`/`organizationId` additionalFields plus the `user.update.before` hook throwing on those fields = two layers against self-assignment (verified in `server.ts:111-160, 195-214`). Invited email joins the inviting org with the invite role; otherwise a fresh org is created and the user becomes its SUPER_ADMIN. `requireEmailVerification: true` blocks sign-in until verified.
- **Login:** wrapper `POST /api/auth/login` → `auth.api.signInEmail` (scrypt via better-auth Account model); generic `invalid_credentials` on failure (no enumeration here); 2FA redirect honoured with pending-2FA cookie forwarded. Rate limits: wrapper 10/min/IP fail-closed + better-auth 3/10 s on `/sign-in/email`.
- **Logout:** `POST /api/auth/logout` → `auth.api.signOut`, Set-Cookie forwarded so the browser drops the cookie.
- **Email verify / password reset:** better-auth defaults verified in installed `1.7.26`: reset token expiry 3600 s (`dist/api/routes/password.mjs:73`), verification token expiry 3600 s default (`dist/api/routes/email-verification.mjs:14`); `revokeSessionsOnPasswordReset: true`. Reset/verification URLs are emailed via `mailer.ts`, which never logs bodies (preview mode behind explicit `EMAIL_LOG_PREVIEW=true`).
- **OAuth (Google sign-in):** same Google Cloud app as data connections; `accountLinking: { enabled: true, trustedProviders: ["google"], requireLocalEmailVerified: true }` blocks the account-pre-hijack vector (unverified local account cannot be linked). Social login is only enabled when both client id/secret are configured.
- **OAuth (data connections):** PKCE S256 (`packages/google/src/oauth.ts:53-60`), state nonce HMAC-signed with `SESSION_SECRET` (fail-closed if <32 chars; constant-time verify, `packages/shared/src/crypto.ts:98-115`), persisted single-use state consumed atomically (`consumeOAuthState`, `updateMany` + `consumedAt`, 10-min TTL), session binding (`callback` checks `sessionUser.id === flow.userId`), org binding re-check, owner-access re-check at callback, `prompt: consent` + `access_type: offline` for refresh tokens. No refresh token → explicit `no_refresh_token` redirect, no unusable connection stored.
- **Invite accept:** token is `randomBytes(32)` hex, SHA-256 hash stored; accept requires email match and moves the user only from an empty shell org (A-SEC-20).
- **User delete:** admin path `DELETE /api/members/[id]` (self-delete and last-SA blocked; blocked while the user created connections or initiated transfers — Restrict FKs). better-auth's own `POST /api/auth/delete-user` is **disabled by default**: installed `better-auth@1.7.26` returns 404 unless `user.deleteUser.enabled` is set (`dist/api/routes/update-user.mjs:246`), and the app does not set it — verified, not a hole.
- **Sessions:** 30-day sliding, `httpOnly`, `SameSite: lax`, `secure` cookie prefix in production (`useSecureCookies: NODE_ENV === "production"`; better-auth defaults verified in `dist/cookies/index.mjs`: `httpOnly: true, sameSite: "lax", secure: <prefix>`). CSRF: better-auth origin-check middleware validates Origin/Referer against trusted origins and `callbackURL`/`redirectTo` against trusted origins (verified in `dist/api/middlewares/origin-check.mjs`); app's own cookie-authenticated API routes rely on `SameSite=lax` alone (no per-request CSRF token) — acceptable for same-origin use, noted as a residual.
- **2FA:** TOTP plugin enabled; enrolment voluntary (A-SEC-08); `freshAge: 15 min` configured but not enforced on app routes (A-SEC-02).

## Tenant isolation (revalidated)

- **Cache keys:** `buildCacheKey` (`packages/shared/src/cache.ts:56-72`) is `analytics:{organizationId}:{websiteId}:{propertyId}:{source}:{report}:{range}:{filters}` — org is always the second segment; invalidation is by org/website prefix scan (`SCAN`, not `KEYS`). **PASS.**
- **Snapshots:** `writeSnapshot`/`readSnapshot` keyed by the same cache key; `invalidateOrgSnapshots` deletes by `cacheKey startsWith analytics:{orgId}:` (`packages/db/src/snapshots.ts`). **PASS.** One caveat: `readSnapshot` returns `updatedAt: row.createdAt` (upserts do not bump `createdAt` in Prisma unless the row is recreated — check: `AnalyticsCache` upsert updates `payload`/`expiresAt`/`websiteId` but `createdAt` stays the original creation time, so `snapshotUpdatedAt` can under-report freshness on long-lived rows; P3 functional note, see A-API-14).
- **Analytics handler:** `apps/web/src/lib/analytics-handler.ts` — auth → permission → zod query validation → `assertWebsiteAccess` → connection resolution org-scoped (`packages/google/src/client.ts: resolveConnectionForWebsite` filters `organizationId: website.organizationId`) → primary integration → cache → snapshot → live (single-flight lock). **PASS** for isolation; rate limiting absent (A-SEC-07).
- **Connection scope:** `assertConnectionScopeForWebsite` (`tenant.ts:36-54`) blocks cross-team credential binding at map time; `resolveDiscoveredProperty` (map route) only accepts properties discovered under the caller's org connections. **PASS.**
- **DB backstops:** composite FKs `(id, organizationId)` on TeamMember/WebsiteAssignment (`schema.prisma:257,304-306`), `@@unique([organizationId, domain])` on Website, partial unique index for single-open-transfer (referenced in transfer route), single-primary partial unique index (referenced in map route). **PASS** as designed; last-admin guards now have a transactional backstop — `SELECT … FOR UPDATE` + in-transaction count (A-SEC-18, fixed 2026-11-24).

## Injection / XSS / SSRF / redirects (revalidated)

- **Prisma/SQL:** no string-built SQL anywhere; only raw SQL is the literal `` prisma.$queryRaw`SELECT 1` `` in health/ready and the worker. All user input goes through Prisma parameterized queries or zod-validated values. **PASS.**
- **XSS:** zero occurrences of `dangerouslySetInnerHTML` in `apps/` and `packages/` (grep). React escaping throughout; CSV export neutralizes formula injection (`apps/web/src/lib/csv.ts: csvCell` prefixes `= + - @` cells with `'`). **PASS.**
- **Open redirect:** OAuth callback redirects are built only from `NEXT_PUBLIC_APP_URL` (env) + fixed paths; connect redirects to a Google-generated URL; better-auth `callbackURL` values are validated against trusted origins (origin-check middleware, verified in installed library). No user-controlled redirect target found. **PASS.**
- **SSRF:** no user-controlled `fetch()`/URL in the app. Google clients call fixed `googleapis` hostnames (`packages/google/src/ad-manager.ts:27`, ga4/search-console/adsense/discovery); `propertyId` is interpolated into GA4 `properties/{id}` request fields but only ever comes from a DB mapping that was validated against a discovered property — not attacker-controlled. `bullConnectionOptions` parses `REDIS_URL` (server config only). **PASS.**
- **Secrets/crypto:** AES-256-GCM envelope `v1:<keyId>:<base64(iv|tag|data)>`, AAD bound to connection identity (`connectionAad`), key rotation via `GOOGLE_TOKEN_ENCRYPTION_KEY_PREVIOUS`, legacy ciphertexts re-encrypted lazily, unknown key ids / future versions fail loudly (`packages/shared/src/crypto.ts`). Refresh-token rotation handled with a Redis lock + fencing check (`packages/google/src/tokens.ts`). **PASS.**
- **Redaction/audit:** `scrubAuditDetails` drops credential-shaped keys recursively and redacts secret-shaped substrings in values (`packages/db/src/audit.ts`, `packages/shared/src/redact.ts`); `sanitizeProviderError` bounds + redacts provider errors before logging/storage; mailer never logs bodies. **PASS** (one gap: `GET /api/sync/failed` exposes stored `lastError` cross-tenant — the value is sanitized at write time, but the endpoint is still the A-SEC-01 leak).
- **Security config:** nonce CSP (`script-src 'self' 'nonce-…' 'strict-dynamic'`, no `unsafe-inline` for scripts; `style-src` keeps `unsafe-inline`; `img-src 'self' data:`; `frame-ancestors 'none'`) in `apps/web/src/proxy.ts` (fresh nonce per request; matcher excludes `_next/static` and image assets — acceptable for static files). Static headers in `next.config.ts` (nosniff, `X-Frame-Options: DENY`, referrer-policy, HSTS, permissions-policy). Gaps: A-SEC-13. **Mostly PASS.**
